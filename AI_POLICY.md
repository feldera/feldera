# AI Policy

We use AI at Feldera and welcome contributions made with it. But AI makes code cheap to produce, so reviewing it is now more work than writing it.

Our goal with this policy is to keep contributions high quality, easy to review and a fair use of our time.

## Drive-by AI contributions

Open-source projects these days are being spammed with drive-by submissions. These are submissions generated by AI tools and opened by people with no stake in the project. These submissions are usually unhelpful:

- **The submitter doesn't understand the change.** It looks plausible but often misses the actual problem or ignores how Feldera works, which leaves all the verification to us.
- **The submitter isn't a user.** They don't use Feldera, so they can't relate to the problem or judge whether the fix is right in practice.
- **They don't own it afterwards.** They are gone after the merge, and when the change breaks something, we are left to debug and fix it.

We hold every contribution to the same bar, whoever submits it. We want contributors who use Feldera, understand their change, and stick around to maintain it.

With that goal in mind, here are the guidelines for contributing to the project.

### 1. Start with a design

For any non-trivial change, file an issue using the [RFC template](https://github.com/feldera/feldera/issues/new?template=-rfc--design-of-a-new-feature.md) with a short design document before writing code. See [Trivial changes](#4-trivial-changes) for what does not need a design.

A good RFC is:

- **Human-written and concise.**
- **Clear.** It states the problem and the proposed solution plainly.
- **Top-down.** It goes from goal, to approach, to key decisions, and only then to details.

Please wait for a maintainer to approve the design before opening a pull request.

### 2. AI-assisted code is fine, but you must understand it

You may use AI to write code. But you are still the author and you must understand every part of it:

- the design decisions and why alternatives were rejected
- the logic, invariants, and performance implications
- the comments
- the names of variables, functions and types and what they represent

**Code that looks like unreviewed AI output will be rejected.**

### 3. Pull requests

- Link the issue and the approved design.
- Write the PR description and review replies yourself.
- Disclose AI use in the PR description: name the tool and say what it did.

### 4. Trivial changes

Small fixes don't need a design document. These include typos, documentation corrections, and obvious one-line bug fixes. Everything else in this policy still applies.

### 5. Enforcement

Maintainers may close without detailed review any issue, design or PR that:

- is AI-written prose,
- is needlessly long,
- contains code that looks like slop, or
- skips the design step when one is required.
